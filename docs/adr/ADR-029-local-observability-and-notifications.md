The owner explicitly reaffirmed **CORE LIGHT LUNA FIRST** after reviewing premature P0 synthetic observability/event source work. This ADR remains a **record of future architectural requirements only**, not a current implementation task or authorization to deploy metrics, Grafana, notifications, API servers, provider adapters, durable outbox or additional synthetic telemetry code. ## Owner decision

Light Luna **must** provide a documented **Prometheus-compatible metrics API** consumable by a Prometheus server and Grafana, showing **ban state and security/health statistics**; it must also provide owner-configured outbound notifications through **Telegram, Discord, Slack and email (SMTP)**. Observing the number of blocks alone is insufficient: the product must distinguish observed attacks, proposed decisions, approved decisions, executor-applied vs failed/reverted/expired bans, health, freshness and evidence quality. See the [concrete contract](../architecture/local-observability-and-notifications.md).

**Stage and reality:** these are **decided future product requirements**, not evidence of existing HTTP endpoints, token handling, backend integrations, dashboard JSON, running notifier or kernel-applied bans. All implementing code and integration acceptance gates remain unstarted. This ADR does not itself authorize production changes or sending a test message.

## Architectural boundaries — non-negotiable

1. **Standalone-first / offline-first:** real local monitoring state and event history must work without Prometheus, Grafana, Telegram, Discord, Slack, SMTP, Cloud or NetBird. Collector/snapshot/reporting and exporter/notification are separate, unprivileged, **non-authoritative** processes or bounded modules. No network connector is a dependency of Policy Gate, watchdog, nft, ban expiry or emergency owner recovery. Initial P0 remains no actual ban enforcement. NetBird remains **strictly deferred** until independently verified G-STANDALONE **and explicit owner approval**.
2. **Metrics vs detailed evidence:** a local, opt-in Prometheus text/OpenMetrics-compatible `GET /metrics` provides numeric aggregates with predictable low-cardinality label sets, not individual ban IPs, raw URLs, usernames, email addresses, token/tenant/device IDs or unbounded event/rule IDs. Grafana consumes Prometheus as a **data source**, not a proprietary Grafana-specific firewall protocol. A separately authenticated, paginated **read-only** local security API returns owner-scoped ban/event records when supported. Plain exporter alone must never imply individual actor forensics or current kernel enforcement without a trusted applied-state receipt.
3. **Local privacy and exposure:** metrics/export/API default **disabled unless owner config enables**, `127.0.0.1`/Unix socket binding, optional protected proxy for remote Prometheus, TLS/mTLS or signed scoped access, independent permissions, no accidental public `/metrics` or admin API. Harden HTTP against resource exhaustion, bounded scrape/render, listener limits, and authorization failures. Grafana dashboard grants are **not a substitute for data-source credentials and row-level access**.
4. **Notification isolation:** a local bounded spool/outbox accepts only normalized trusted audit events **after** policy decision/verified receipt (e.g. block applied vs suggested, rollback, unusual scan, offline/degraded, integrity drift). A worker maps severity/configured route to Telegram Bot API, Discord webhook, Slack incoming webhook, or SMTP message. Workers **cannot call Policy Gate to ban/unban**, execute shell, alter host firewall or block packet processing; sending and provider outages must be asynchronous and nonblocking.
5. **Delivery correctness:** dedupe/group noisy repeated scans, cool-down/throttle, bounded exponential backoff+jitter, TTL/retry budget, durable last-attempt/cursor, dead-letter/manual retry. At-least-once delivery where supported with potential duplicates; never promise exactly-once for external providers. Mark `queued/sent/failed/expired/suppressed` separate from `ban applied`. Feedback and recipient acknowledgments do not imply enforcement success. Alerts must support retraction/unban/false-positive corrections and a critical-path escalation rule without creating alert storms.
6. **Secrets and data minimization:** bot tokens, webhooks, SMTP credentials and recipient addresses live in protected local credential store/config, never metrics, plain exports, Git/docs or log messages. Default outbound template includes time, local instance alias, event category, severity, action/verdict status, bounded count, expiry and local evidence link **without raw source IP/full URL**. Optional owner-controlled sensitive detail sharing must be channel-specific, scoped, redacted, with explicit opt-in/retention/audit; do not send raw packet payload, HTTP bodies, secrets, private device topology or unreviewed Cloud identifiers. Prevent mentions/pings via untrusted inputs in Discord/Slack/Telegram and sanitize HTML/Markdown/email headers.
7. **Bounded resources:** fixed event ring/queue and per-provider quota, worker concurrency ceiling, response body/URL allowlists, fixed-time retries, low-cardinality metric registry, HTTP timeouts, protection against DNS/redirect-based SSRF to metadata/private admin addresses; no arbitrary user-provided callback/webhook URL without validation. Telemetry degradation must be observable but never a justification for unapproved auto-block.
8. **Versioning and portability:** versioned Go-owned event/ban snapshot schemas and stable metric names. Local SQLite (proposed) or another durable store is not assumed implemented. A future Cloud/fleet aggregate must be explicit owner-opt-in with multi-tenant isolation and no kernel write authority; at least one local-only mode must survive complete outbound shutdown. Packaging and independent adapter updates follow ADR-024/025 compatibility and signed rollback rules.

## Proposed delivery milestones and acceptance (not yet built)

- **P0:** document contracts and use pure, synthetic read-only tests to verify statuses, no secret/IP labels, disabled-by-default and no code path into kernel/policy execution. No HTTP port opened on HOMESV for this ADR.
- **P1 / standalone base:** owner-authorized local status read model, bind-restricted metrics exporter and authenticated read-only ban/event API, initial Grafana dashboard for bans/decision action and health; ensure actual executor receipt is the source of applied-state, not a Brain suggestion.
- **P2:** opt-in local outbox and 4 provider adapters, templates EN/VI, notification lifecycle/health, retry/dedupe/backpressure, delivery simulation and offline reconnection tests. No provider credentials included in tests or repository.
- **Before G-STANDALONE release acceptance:** documented instrumented reliability, memory/disk/cpu/cardinality limits, denied unauthorized scrape/detail reads, no host lockout when exporter is unavailable, negative SSRF/credential-leak tests, offline no-provider functionality, verified event-to-applied receipt match; dashboards and notifications must not misrepresent non-enforced advisory bans.
- **Later optional:** Grafana Loki log correlation, Alertmanager integration, Cloud aggregation, fleet dashboards, provider OAuth variants, NetBird-compatible transport (only after explicit standalone gate/owner approval). None required for standalone operation.

## Alternatives and migration

Prometheus exporters (pull) and provider adapters (push) are separate to avoid making a network/event bus a mandatory firewall component. Do not send every attacker IP as a Prometheus label or turn Grafana webhooks into a rule executor. Migration from synthetic current P0 snapshots to live ban state requires a trusted typed executor receipt, reconciliation for unknown/expired bans, schema versioning and owner-reviewed recovery semantics.
