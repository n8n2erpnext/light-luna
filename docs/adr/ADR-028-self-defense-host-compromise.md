# ADR-028 — Light Luna Self-Defense, Host Compromise Detection and Collective Trust Containment

Status: **DECIDED architectural requirement; implementation NOT STARTED**
Date: 2026-10-14
Scope: client integrity, Linux malware/ransomware/host-compromise detection, safe containment, Cloud ingress trust, prevention of lateral/collective spread
Supersedes: none; extends [ADR-021](ADR-021-ebpf-observability-xdp-optional.md), [ADR-024](ADR-024-offline-base-independent-component-updates.md), [ADR-026](ADR-026-unified-account-remote-fleet-control.md) and [ADR-027](ADR-027-collective-threat-immunity.md)
Primary sources: [Host defense and trust-containment architecture](../architecture/host-self-defense-and-compromise-containment.md), [Security](../07-SECURITY-SAFETY.md), [Brain V2](../architecture/luna-brain-v2.md), [Cloud collective intelligence](../architecture/federated-immune-threat-intelligence.md)

## Problem and product decision

A security agent with possible future eBPF/XDP/kernel privilege and Cloud synchronization is itself an attractive target. **Light Luna must protect its own binaries, policies, signing/updater and privileged interfaces, detect supported classes of compromised-host behavior, and prevent unverified or compromised-node submissions from poisoning Cloud knowledge or triggering unsafe defensive decisions on other nodes.** Treat **every** node contribution as untrusted regardless of enrollment or signature. A compromised node must never obtain authority to publish globally trusted scenarios, modify another node's configuration, access other tenants or turn a malware artifact into a distributable KnowledgePack.

The mandatory split is **Guard the Guard / Detect the Host / Contain the Client / Quarantine Cloud Ingress / Recover from Trusted State**, with independent authority, explicit product modes, testable fallback and signed update provenance.

**CRITICAL clarification:** XDP processes inbound packets at an early network hook; **it cannot scan process memory, files, ransomware activity or rootkits by itself.** Host signals need eBPF tracing of supported exec/socket/file/credential hooks, Linux logs, proc/process provenance, filesystem integrity measurement, package/asset checks and optional **resource-bounded antivirus/signature/YARA-style on-demand or fanotify-based on-access scanners**. None of these, alone or combined, guarantee detecting all malware. Severe root/kernel compromise can falsify host telemetry, including eBPF output. Treat device integrity confidence as `UNKNOWN` unless evidence is adequate; use optional hardware-backed attestation or trusted rescue/off-host evidence where feasible. **No Light Luna eBPF/XDP code, loader, malware engine or scanner currently exists.**

## Non-negotiable security boundaries

1. **Least privilege:** split unprivileged Go Brain/collectors/Cloud agent, dedicated restricted nftables executor, separately privileged BPF loader, independently supervised updater/safety watchdog and narrowly scoped local credential/key broker. No dynamic scripts, arbitrary commands or unsigned plugin execution from CVE text, Community scenarios or client signals. SELinux/AppArmor, systemd sandboxing, read-only paths, capabilities, seccomp, private tmp and per-component resources as tested.
2. **Guard executable integrity:** verify signed version manifests and immutable artifact digests at install and before activation; protect policies, owner allowlists, updater, trust-root store, local audit and BPF map/links from unprivileged mutation. Detect unexpected binary/config hash drift, unauthorized policy/systemd changes, BPF attachment replacement and suspicious permission/capability escalation. Evaluate IMA/fs-verity/TPM **when supported**, never assume universal kernel or filesystem support.
3. **Observe host behavior before act:** correlate process trees, exec ancestry, abnormal privileges/capabilities, suspicious persistence/scheduled services, cryptomining/CPU pressure, mass file-renames/encryption-like writes, unexpected outbound C2-like DNS/TLS/network, lateral SSH/SMB/RDP scans and compromise of local control sockets. Include allowlisted maintenance/backup/updater benign alternatives and evidence quality; avoid pretending encrypted payload content is visible.
4. **Independent guardian:** a minimum self-integrity health subsystem is needed even if Brain crashes. Its decisions are fixed policy, not learned authority. The Brain may recommend; high-risk quarantine uses local owner policy + restricted executor + rollback. Do not let suspicious telemetry drive an automatic global network isolation rule that cuts off SSH, management, incident response, monitoring, or Cloud safety controls without explicit safe design.
5. **Containment modes:** `NORMAL`, `SUSPECTED`, `LOCAL_QUARANTINE`, `FLEET_QUARANTINED`, `RECOVERY_REQUIRED`. Quarantine should preserve deterministic emergency management and local firewall, take a minimal evidence receipt, and stop high-risk cloud contributions/remote changes. Where owner-authorized, restrict selected malicious egress/lateral targets by nftables, preferably scoped by process/service/network with TTL; **not blanket Internet loss by default**. Unsupported cgroup/process mapping → alert or manual containment instead of guessing.
6. **Cloud distrust by default:** client identity proofs authenticate a device, **not the cleanliness of its OS**. Internet-ingress Cloud parser enforces schema/bytes/rate/schema-version/tenant boundaries, replay/nonces, validated signatures and expiry, quarantines raw submissions in a non-executable store, filters prohibited data and strips instructions/active payloads. Distinct non-privileged intake worker, analysis service, publisher and offline/key-isolated signing service; client submissions cannot reach signer private keys or another tenant's inbox. A compromised node's reports never directly alter global reputation, signed scenario packs or device fleet commands.
7. **Trust state machine + revocation:** separate `deviceAuth` from `deviceIntegrity` and `communityContributionTrust`. Cloud can revoke compromised device credentials and suspend intelligence contribution/remote management, while local offline firewall continues. Suspicious/compromised devices are excluded from quorum and cannot amplify their own allegations through cloned identities. Signed revocations and false-positive retractions propagate to other clients; no indefinite cached `CLEAN` badge.
8. **No malware-sample sharing by default:** Never upload raw file binaries, suspicious scripts, memory dumps, raw packet captures, personal files or executable payloads in normal community signal channel. Share only opt-in minimized behavior features/digests and reviewed non-executable hashes. If a future separate lab allows suspicious specimen transfer, require explicit owner approval, dedicated isolated scanner/analysis with no publication/upload path and a separate compliance/retention/security review.
9. **Critical compromise response:** if kernel/root trust is lost, Light Luna cannot prove its own integrity or self-heal reliably; mark `UNTRUSTED/RECOVERY_REQUIRED`, suspend sensitive Cloud authority and guide owner toward trusted external console/live rescue, rotation/revocation of keys, forensic snapshot (as appropriate), clean reinstall from known-good signed images and inventory checks. Do not declare `CLEAN` because an on-host scan passed.

## Capability tiers and release gates

- **Base release required:** self-integrity verification for signed artifacts/config, least-privilege components, local audit and tamper alarms, bound and validate all Cloud input/output, guarded protected management, independent rollback and **honest unsupported/degraded status**. Local firewall must run with no Cloud/EDR.
- **Host Guardian Basic (P1/P2 staged):** process/network/host log observation, process lineage/exec/privilege/persistence/egress heuristics and simple hash/SBOM policy with bounded memory and benign replay. Kernel eBPF tracing optional and capability-gated; safe OS logs/proc/fanotify fallbacks when available. No blanket malware-clean claims.
- **Optional deeper scan (P2+):** separate least-privileged ClamAV/engine for **selected file trees** (on-demand default), typed signature updater independent of Brain/knowledge; scoped on-access prevention requires operator opt-in and deadlock/IO performance testing. Optional YARA-style research signatures are data-only in constrained offline worker, not a command/macro interpreter.
- **Containment (P3):** owner-defined per-service/host protections, local Policy Gate, bounded TTL, independent watchdog and out-of-band recovery verified in isolated VMs. Do not automatically SIGKILL system daemons or freeze all host egress from one signal.
- **Collective trust (P7 optional Cloud):** multi-tenant untrusted-intake quarantine, provenance scoring, device quarantine/revocation, malicious signal/replay/anti-poisoning tests, fleet warning/watch and clean-room global review/publishing with no client code execution.

## Evidence and open engineering issues

Reference [Tetragon](https://tetragon.io/docs/overview/) (eBPF exec/file/network observability), [Falco](https://falco.org/docs/) (syscall/rule-based host behavior), [Linux IMA](https://github.com/linux-integrity/ima-doc/blob/main/ima-concepts.rst) / [fs-verity](https://www.kernel.org/doc/html/latest/filesystems/fsverity.html) (file integrity), and [ClamAV on-access](https://docs.clamav.net/manual/OnAccess.html) (fanotify-based scanner), all as **potential architectural precedents**; do not install them or claim they replace host attestation. Separate checks and false-positive benchmarks are needed for kernel/driver/arch/containers, file scanner coverage, ring buffer loss, CPU/RAM thresholds, reboot and power failure, CVE/IOC poison, device cloning, signer isolation and emergency reachability.

This is a **product requirement and threat model, not a shipped endpoint protection suite/EDR/antivirus or currently active scan**. Implementation and measured malware detection coverage remain open. No current machines, BPF attachments, daemon services, firewall, Cloud or NetBird are modified by this ADR.
